# План виводу пошуку магазину в реліз

Оновлено 2026-07-25 після профілювання dev БД і реалізації hybrid catalog.

## 1. Рішення

Пошук магазину використовує гібридну модель:

- Elasticsearch індексує повний статичний web-каталог.
- SQL гідратує актуальну ціну та залишок лише для кандидатів поточного запиту.
- Наявність на складі не визначає, чи товар існує в каталозі.
- Відкривати додаткові склади через `ForEcommerce` для збільшення каталогу не потрібно.

Це розділяє дві різні відповідальності:

1. ES відповідає за текстовий пошук, релевантність, артикули, OE-номери та стабільну пагінацію.
2. SQL є єдиним джерелом істини для комерційних даних, які можуть змінитися між двома запитами.

## 2. Контракт каталогу

До ES потрапляє товар, якщо:

```sql
Product.Deleted = 0
AND Product.IsForWeb = 1
AND товар є канонічним хоча б для одного джерела (Fenix або AMG)
```

На dev:

| Метрика | Значення |
|---|---:|
| Активні товари | 373 209 |
| Активні `IsForWeb = 1` | 373 208 |
| Попередній stock-gated каталог | 12 209 |

Різниця не означає, що в магазині треба показувати фіктивний залишок. Товар може бути
знайдений у каталозі, але отримати `AvailableQty = 0` після live-гідратації.

Комерційні поля в ES не є authoritative. Під час статичної проєкції вони записуються як
нульові compatibility-поля, а під час читання не використовуються:

- `RetailPrice*`
- `AvailableQty*`
- `CatalogScopes`
- pricing/availability revision markers

Версія схеми: `web-catalog-v5-live-sql`.
Конфігураційний підпис: `web-catalog-live-sql-v1`.

## 3. Flow пошукового запиту

1. ES повертає впорядкованих кандидатів за статичними полями товару.
2. Сервер бере кандидатів батчами до 100, максимум 10 000 на один запит.
3. SQL одним bounded-запитом рахує ціни для кандидата та договору.
4. Кандидати без доступної ціни відсіюються до пагінації.
5. Після визначення сторінки SQL один раз дістає залишки лише для товарів цієї сторінки.
6. API повертає ES-опис товару з live-ціною та live-залишком.

Для порожнього запиту порядок стабільний: `NameUA/Name`, потім `Product.ID`.
Залишок не впливає на присутність товару в каталозі й не береться зі старого ES-документа.

Live SQL додатково перевіряє:

- активний договір і його організацію;
- VAT-гілку;
- source world організації;
- source marker товару;
- валюту;
- склад `ForEcommerce = 1`, `ForDefective = 0` та точну організацію.

Від'ємний агрегований залишок назовні повертається як `0`.

## 4. Flow синхронізації ES

### Повна перебудова

- Кандидати читаються по `Product.ID` батчами.
- SQL-проєкція не викликає scalar pricing UDF і не джойнить залишки.
- Ціни та наявність не є причиною повної перебудови.
- Нове покоління стає активним лише після завершення generation fencing та alias promotion.

### Інкремент

Інкремент відстежує тільки зміни пошукового документа:

- `Product`;
- `ProductOriginalNumber`;
- `OriginalNumber`;
- `ProductSlug`.

Алгоритм materialize-first:

1. прямі зміни записуються у `#DirectChangedProductIds`;
2. повний набір, включно з exact source siblings, записується у `#ChangedProductIds`;
3. сторінка ID читається з матеріалізованого набору;
4. проєкція виконується окремо лише для отриманих ID.

Це прибирає повторне розгортання великого CTE всередині проєкції. Видалення канонічного
товару також переіндексовує його активного source sibling.

Щоденна повна перебудова та orphan probe залишаються страховкою від масового 1С re-mint.

## 5. Виміряні результати

Заміри виконані 2026-07-25 на dev SQL Server.

| Операція | Результат |
|---|---:|
| Старий incremental CTE | не завершився за 30 с; deployed worker падає по timeout 120 с |
| Новий incremental plan, без змін | 227-245 мс |
| Новий incremental plan, 1 змінений товар | 425-577 мс, 1 ID |
| Статична проєкція 2 000 товарів, warm | близько 429 мс |
| Статична проєкція 20 000 товарів | 3 405 мс |
| Live-ціна для 100 source-matching ID | 320 мс; 69 позитивних |
| Live-залишок для 20 ID | 61 мс |

SQL-швидкість статичної проєкції становить близько 5,87 тис. товарів/с. Груба оцінка
SQL-частини повного каталогу 373 тис. товарів: близько 64 с. Це не включає ES bulk,
original numbers, alias promotion і мережеві витрати; фактичний end-to-end час треба
заміряти після dev-деплою.

Попередня повна перебудова займала 417 с, бо виконувала scalar pricing UDF для всього
каталогу. Цей UDF більше не входить у rebuild.

## 6. Перевірки коду

Виконано:

- unit suite після materialization-правки: 312/312;
- focused incremental suite: 16/16;
- реальна SQL Server integration у disposable DB: 2/2;
- integration довела exact source-sibling reindex, включно з deleted canonical.

Release build: 8/8 проєктів, 0 errors, 0 warnings. `git diff --check` чистий.

API suite проти старого dev-контейнера не є перевіркою цього diff:

- 70 тестів пройшло;
- 16 впало;
- deployed dev не має release-ready active generation;
- логи deployed worker містять старий `GlobalRetailDependencyChanges` і timeout 120 с.

Ці падіння фіксуються як baseline старого контейнера. Закривати їх послабленням тестів
заборонено.

## 7. Dev cutover

1. Зібрати й задеплоїти новий образ `gba-ecommerce-api`.
2. Переконатися, що контейнер використовує schema `web-catalog-v5-live-sql`.
3. Запустити одну повну перебудову.
4. Дочекатися успішного alias promotion.
5. Перевірити кількість документів: очікується близько 373 208, а не 12 209.
6. Перевірити артикули з Fenix-only, AMG-only та dual-source.
7. Для кожного кейсу звірити ціну з договором/source world у SQL.
8. Перевірити нульовий, позитивний і від'ємний залишок.
9. Змінити товар, slug і OE-номер; перевірити інкремент не довше одного інтервалу.
10. Видалити canonical рядок тестового source pair; перевірити promotion sibling без дубля.
11. Запустити API suite проти нового контейнера.
12. Заміряти повний rebuild, incremental p50/p95 і search p50/p95.

Критерій виходу:

- health/search ready;
- активний alias вказує на нове покоління;
- немає SQL timeout;
- каталог не stock-gated;
- ціни та залишки відповідають live SQL;
- повторний incremental нічого не дублює;
- API regression зелений або кожна незалежна baseline-помилка задокументована.

## 8. Production gates

До prod потрібні:

1. успішний dev cutover з повним rebuild;
2. виміряний end-to-end час перебудови;
3. rollback на попередній alias/image;
4. алерт на відсутність active generation, lag watermark і повторні sync failures;
5. перевірений Change Tracking bootstrap на prod;
6. окреме maintenance window для першого покоління;
7. smoke пошуку, картки, кошика й оформлення замовлення після promotion.

Не потрібно:

- відкривати додаткові склади для збільшення кількості товарів;
- зберігати ціну або залишок у ES;
- перебудовувати ES після кожної зміни ціни чи залишку;
- підміняти повний каталог лише товарами, які зараз є в наявності.

## 9. Відомі залишкові ризики

1. Повний rebuild ще не заміряний end-to-end на новому образі.
2. Live price кандидатів обмежений 10 000; широкі запити повинні мати observability для
   випадків, коли перші цінові товари лежать за цією межею.
3. Інкремент матеріалізує весь change set один раз у пам'яті перед chunked-проєкцією.
   Для масового оновлення сотень тисяч статичних товарів це кілька мегабайт ID, але такий
   сценарій все одно потрібно моніторити й за операційною процедурою переводити у full rebuild.
4. Fallback на SQL `ProductSearchToken` не входить у цей diff; відсутність active generation
   усе ще fail-closed.
5. `EPPlus 8.5.4` тягне вразливий `System.Security.Cryptography.Xml 10.0.7`; dependency
   має бути оновлена до безпечного релізу перед production build.
